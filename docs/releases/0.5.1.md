# 0.5.1: plugin hooks check only what the session wrote

**Status: released on `main`, 2026-11-05.**

| Plugin | Version |
|---|---|
| `hobin-feature` | 0.5.0 → 0.5.1 |
| `hobin-review` | 0.5.0 → 0.5.1 |
| `hobin-stances` | 0.5.0 → 0.5.1 |
| `hobin-learning` | 0.5.0 → 0.5.1 |
| `hobin-skill-eval` | 0.3.0, unchanged |

Specs are unchanged. This release fixes how the plugin hooks from 0.5.0 decide what to
check (#4, #5).

## What went wrong in 0.5.0

0.5.0 moved the result hooks into every session and had them check "results written in the
session", meaning files changed after the session transcript was created. In real use that
rule failed in four ways:

- **Other sessions' files.** A session opened at a parent folder (`~/coding`, not a
  repository) claimed records that other sessions wrote under it. The hobin-feature Stop hook
  then ran `scenarios.mjs check` over every record in the tree: 701 records, 121 of them
  incomplete.
- **Links crashed the walk.** The record walk followed symbolic links. A dangling link
  (`.bin/bcrypt`) crashed it with ENOENT; a link to an ancestor crashes it with ELOOP. The
  hook reported the crash as an incomplete record (exit 2), and Claude Code labeled it
  "Hook script appears to be missing".
- **Checkouts looked like results.** After `git worktree add` in a session, every checked-out
  file was "changed in the session". The review and stances hooks blocked on untouched eval
  fixtures (`core/review/scenarios/*/golden/REVIEW.md`) and `core/applying-stances/SPEC.md`,
  three times per cycle, for the rest of the session.
- **Checks switched off silently.** In the result hooks' walk, one dangling `.md` link or
  locked folder threw, and the hook exited 0. The check was off without any message.

## Changes

- **Ledger.** All four hooks now keep a per-session ledger of what the session's own tool
  calls wrote, and Stop checks only that ledger. Nothing walks the tree on Stop.
  - Edit tools (Write/Edit/MultiEdit, a Codex `apply_patch`) are recorded as written.
  - A shell command that names a record or record script (hobin-feature) or a `.md` file
    (review, stances, learning) adds what changed since its `PreToolUse` stamp. That means
    the files it names, and records under its cwd for hobin-feature or files found by name
    under its cwd for the result hooks. Stamps are keyed by `tool_use_id`. Without a usable
    stamp, only named files changed during the session count.
  - Claude reports a command that exited non-zero as `PostToolUseFailure`, so that event is
    registered too.
- **Files git wrote.** A file that git tracks, still holds as committed, and last committed
  before the call was written by a checkout, worktree, or pull, so it does not count. The
  rule reads the file's state, not the command text. A result written, or written and
  committed, in the same command as a checkout still counts.
- **Shell feedback.** The result hooks now check results written by shell commands on
  `PostToolUse`, not only on Stop.
- **Crashes.** A checker that throws exits 1: the user sees it and the model is not sent back.
  A record that is not valid JSON is still sent back (exit 2).
- **Safe walks.** No walk follows symbolic links, and an entry that cannot be read is skipped.
  hobin-feature has one walker, `scripts/records.mjs`, shared by `scenarios.mjs`,
  `compile-control-model.mjs`, and the hook. Dot directories are still searched.
- **Record roots.** When a session runs from a folder outside any repository, hobin-feature
  checks each record against its own repository root.
- **Explicit paths.** `developing-features` now passes the record path to
  `scenarios.mjs run|check` and `--gate`. Without a path the scripts still take every record
  under the current directory.

## Upgrading

```sh
claude plugin marketplace update hobin
claude plugin update hobin-feature@hobin   # and hobin-review, hobin-stances, hobin-learning
codex plugin marketplace upgrade hobin
```

All four hook scripts changed. In Codex, open `/hooks` in a new session and trust them
again. Claude Code needs a restart or `/reload-plugins`.

A session that started before the upgrade still runs the 0.5.0 hooks.

## Verification

Deterministic, without models, on Claude Code 2.1.316 and Codex CLI 0.166.0:

- `pnpm check` passes with 174 tests, on Node 22.19 and 24 in CI and locally.
  `pnpm check:claude` and `pnpm check:install -- claude|codex` also pass.
- Acceptance records with one test per scenario, each run on both hosts' hook inputs:
  - `docs/plans/acceptance-scenarios-feature-stop-hook-ledger.json`: F1–F25,
    `tests/feature-stop-hook.test.mjs`.
  - `docs/plans/acceptance-scenarios-result-hooks-ledger.json`: R1–R21,
    `tests/result-hooks-ledger.test.mjs`.
- Every scenario that targets a defect fails on the code before its fix. The rest guard
  behavior that must stay, such as shell-written records still being caught.
- An independent verifier reviewed each change three times:
  - #4: NotebookEdit was named but not watched, and an empty or shared stamp claimed every
    record.
  - #5: a session's own `git worktree add` still claimed fixtures. A command-text git rule
    then exempted results that mentioned "git reset" or "am". Finally, a result written and
    committed in one command was exempt.

  Each was fixed with a scenario that fails before the fix. The last fix (commit time before
  the call) came after the third round. A fourth review after the release found no defect in
  it, only a missing scenario (a result in a git-ignored folder must still count); R22 and
  F26 add it.

Live host runs after the release (2026-11-05; model calls, Claude Haiku about $0.02 in all):

- **Claude Code 2.1.316, headless.** A shell write that names its record only by file name,
  after a `cd`, was recorded, so the Pre/PostToolUse pair works through `tool_use_id`. After
  `claude -p --resume` the `session_id` was the same and the next record joined the same
  ledger. A record written by a subagent's Bash call (the main agent used only the Agent
  tool) went into the parent session's ledger. Interactive `/resume` was not tried.
- **Codex CLI 0.166.** The model runs shell commands through the code-mode `exec` tool
  (`tools.exec_command({cmd})`), but hooks receive them as `tool_name: "Bash"` with
  `tool_input.command`. `apply_patch` arrives as `apply_patch` with the patch text in
  `tool_input.command`. Every call has a `tool_use_id`, and `session_id` is the thread id.
  The records were attributed as on Claude Code, and Stop ran.
- **Codex trust.** `codex exec` ran no plugin hook, not even Stop, although `/hooks` had
  trusted them and the app-server's `hooks/list` reported `trusted`. The hooks ran only with
  `--dangerously-bypass-hook-trust`. Whether an interactive Codex session applies the stored
  trust was not checked.

Not rerun: the model evals (regression and trigger). Skill bodies change only in passing the
record path to the scripts, and the hooks are covered by the tests above, not by a model
eval.
