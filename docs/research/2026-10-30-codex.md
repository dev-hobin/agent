## 1. Plugin manifest

- **Root `plugin.json` is canonical.** "For a portable Agent Plugins package, add plugin.json at the plugin root and declare the Agent Plugins schema." Existing `.codex-plugin/plugin.json` files "remain supported as a compatibility fallback." (PB)
- **Required `$schema`.** It must equal `https://agent-plugins.org/schemas/1.0.0/plugin.schema.json`. Otherwise you get the error "root `plugin.json` is not an Agent Plugins manifest" (`codex-rs/utils/plugins/src/plugin_namespace.rs`, `core-plugins/src/agent_plugin_manifest.rs`).
- **Root fields read.** `AGENT_PLUGIN_FIELDS` = `$schema, name, version, description, author, homepage, repository, license, keywords, extensions`. Any other root field logs "ignoring unknown Agent Plugins manifest field" (`agent_plugin_manifest.rs`).
- **Name rule.** Lowercase letters, digits, `.` and `-`; at most 64 characters; no `--` or `..`; must start and end alphanumeric.
- **Fixed component paths.** For the portable format, the code hard-wires `skills: "./skills"` and `mcp_servers: "./mcp.json"`. Docs: "Portable packages discover skills from the root skills/ directory, so the manifest doesn't need a skills field." (PB)
- **`extensions.com.openai` fields:**
  - `apps`, which is "only for registered MCP server mappings in .app.json"
  - `hooks`, which is a path, an array of paths, an inline object, or an array of inline objects
  - `onboardingSkill`
  - `interface`, with `displayName, shortDescription, longDescription, developerName, category, capabilities, websiteURL, privacyPolicyURL, termsOfServiceURL, defaultPrompt, brandColor, composerIcon, logo, screenshots`. The source also accepts `logoDark`. `defaultPrompt` is capped at 3 entries of 128 characters each (`manifest.rs` `MAX_DEFAULT_PROMPT_COUNT/LEN`).
  - Precedence: "When extensions.com.openai is an object, it replaces the entire .codex-plugin/plugin.json overlay … the two aren't merged." (PB)
- **Legacy `.codex-plugin/plugin.json` fields** (`RawPluginManifest` in `manifest.rs`): `name, version, description, keywords, skills` (path or list), `mcpServers` (path or inline object), `apps, hooks, interface, extensions`. Official plugins use this format: all 62 plugins in `openai/plugins` have `.codex-plugin/plugin.json`, and none has a root `plugin.json`.
- **Manifest lookup order.**
  1. Root `plugin.json`, used only if its `$schema` is an agent-plugins.org URI.
  2. Then `DISCOVERABLE_PLUGIN_MANIFEST_PATHS = [".codex-plugin/plugin.json", ".claude-plugin/plugin.json", ".cursor-plugin/plugin.json"]` (`exec-server-protocol/src/lib.rs`).

  Claude manifests are therefore parsed with the same legacy struct. Only the fields listed above are read; `agents`, `userConfig`, `outputStyles` and similar are silently dropped, because serde does not deny unknown fields.
- **Components Codex loads:** skills, MCP (`mcp.json`, or legacy `.mcp.json`), apps (`.app.json`), hooks (default `hooks/hooks.json`), assets, and an onboarding skill.
- **`commands/` is migrated on install.** "#33411 Migrate plugin commands into skills on install" (changelog, 2026-07-21).
  - Source: `command_migration/plugin.rs` reads `commands/` (or the manifest's `commands`) into `.codex-plugin/migrated-command-skills`.
  - It uses `RequireFrontmatter`, which needs a `description`, and `MAX_MIGRATED_COMMAND_SKILL_BYTES = 4_000`.
- **Plugin-root `agents/` is not loaded.**
  - The only `agents` constants in the skill loader are for the per-skill `agents/openai.yaml` (`ext/skills/src/loader/mod.rs`: `SKILLS_METADATA_DIR = "agents"`).
  - Agent roles load only from config-layer folders (see §4).
  - Twelve official plugins still ship Claude-style `agents/*.md` at the root (for example `vercel/agents/ai-architect.md` and `figma/agents/*.md`). Nothing in the loader consumes them. That conclusion is an inference from the source.
  - Docs for Claude plugin conversion: "commands, commands/, agents, or agents/ — Convert reusable behavior to skills… move reusable agent procedures into skills" (https://developers.openai.com/plugins/guides/submit-claude-plugin).
- **Claude compatibility, as documented:** "OpenAI also accepts legacy and Claude-compatible manifests, but new packages should use this format." Hooks get `PLUGIN_ROOT`/`PLUGIN_DATA` "and CLAUDE_PLUGIN_ROOT and CLAUDE_PLUGIN_DATA for compatibility." (PB)

## 2. Marketplace

- **Paths.** Docs list `$REPO_ROOT/.agents/plugins/marketplace.json`, `~/.agents/plugins/marketplace.json`, and the "legacy-compatible" `$REPO_ROOT/.claude-plugin/marketplace.json` (PB). The source also reads `.agents/plugins/api_marketplace.json` and `.cursor-plugin/marketplace.json` (`core-plugins/src/marketplace.rs`).
- **Schema:**
  - Top level: `name` and `interface.displayName`.
  - `plugins[]` entries have `name`, `source`, `policy`, and `category`. "Always include policy.installation, policy.authentication, and category on each plugin entry." (PB)
  - `source` is one of: `{"source":"local","path":"./…"}` or a plain string; `"url"`; `"git-subdir"` with `url, path, ref|sha`; or `"npm"` with `package` (required), `version`, and `registry` (HTTPS only).
  - Local source behavior: "Keep source.path relative to the marketplace root, start it with ./, and keep it inside that root." "If Codex can't resolve a marketplace entry's source, it skips that plugin entry instead of failing the whole marketplace." (PB)
- **Policy enums.**
  - `PluginInstallPolicy = "NOT_AVAILABLE" | "AVAILABLE" | "INSTALLED_BY_DEFAULT"`
  - `PluginAuthPolicy = "ON_INSTALL" | "ON_USE"`
  - Source: `app-server-protocol/schema/typescript/v2/*.ts`.
  - The source also has an optional `policy.products` restriction. It is not documented on PB (`marketplace.rs`).
- **IDs and config.** "The quoted key uses plugin-name@marketplace-name … `[plugins."my-plugin@local-repo"] enabled = true`" (PB). The CLI equivalent is `codex plugin add <PLUGIN[@MARKETPLACE]>` (from `--help`).
- **Cache.** "ChatGPT installs plugins into ~/.codex/plugins/cache/$MARKETPLACE_NAME/$PLUGIN_NAME/$VERSION/. For local plugins, $VERSION is local, and ChatGPT loads the installed copy from that cache path rather than directly from the marketplace entry." (PB)
- **Updates.** "After you change the plugin, update the plugin directory that your marketplace entry points to and restart the ChatGPT desktop app." For Git sources, use `codex plugin marketplace upgrade [name]`. "During marketplace refresh, Codex can install or refresh files for configured plugins, even when enabled = false." (PB) In the CLI: "start a new session before using its bundled skills" (https://learn.chatgpt.com/docs/plugins).

## 3. Skills

- **Discovery paths (SK).**
  - `$CWD/.agents/skills`, then each parent up to the repo root (REPO).
  - `$HOME/.agents/skills` (USER).
  - `/etc/codex/skills` (ADMIN).
  - Bundled skills (SYSTEM).
  - "Codex supports symlinked skill folders." On duplicate names: "Codex doesn't merge them; both can appear in skill selectors."
  - The source also scans `$CODEX_HOME/skills`, commented "Deprecated user skills location … kept for backward compatibility", and project `.codex/skills` (`ext/skills/src/host_roots.rs`).
- **Frontmatter actually read** (`codex-rs/skills/src/parser.rs`):
  - Only `name`, `description`, and `metadata.short-description`.
  - `name` is at most 64 characters and defaults to the directory name.
  - `description` is required. It is collapsed to a single line.
  - All other keys are ignored, including `allowed-tools`, `disable-model-invocation`, `user-invocable`, `context`, `agent`, and `license`. There is no `deny_unknown_fields`.
- **`agents/openai.yaml` schema** (`skills/src/metadata.rs`, `interface.rs`):
  - `interface.{display_name (≤64), short_description (≤1024), icon_small, icon_large, brand_color, default_prompt}`
  - `policy.{allow_implicit_invocation: bool, products: [chatgpt|codex|atlas]}`
  - `dependencies.tools[].{type, value, description, transport, command, url, oauth.callbackPort}`. "Only `mcp` is supported for now." (`skills/src/assets/samples/skill-creator/references/openai_yaml.md`)
  - Docs: "allow_implicit_invocation (default: true): When false, Codex won't implicitly invoke the skill based on user prompt; explicit $skill invocation still works." (SK)
- **Invocation.** "In Codex CLI or the IDE extension, run /skills or type $ to mention a skill." (SK)
  - Plugin namespacing comes from the source: "a skill named `search` beneath a plugin named `sample` is exposed as `sample:search`" (`ext/skills/src/loader/namespace.rs`). Mention characters include `:` (`skills/src/mentions.rs` `is_mention_name_char`), so `$sample:search` works.
  - The `$plugin:skill` syntax is not shown verbatim in the docs (UNVERIFIED in docs, confirmed in source).
  - In ChatGPT the sigil is `@`.
- **Listing budget.** "By default, this list uses at most 2% of the model's context window, or 8,000 characters when the context window is unknown. If many skills are installed, Codex shortens skill descriptions first… Use skills.max_context_tokens … up to 10,000 tokens." (SK)
- **Scripts.** "Prefer instructions over scripts unless you need deterministic behavior or external tooling." (SK) "Use scripts/ when the workflow needs deterministic computation or file processing… Do not add a script when instructions and existing tools can complete the task reliably." (https://developers.openai.com/plugins/build/skills)

## 4. Delegation and subagents

- **Supported and on by default.** "Current Codex releases enable subagent workflows by default." "Current local Codex releases delegate when you ask directly or when applicable AGENTS.md or skill instructions request it." (SA)
- **Tools.** `features.multi_agent` enables "spawn_agent, send_input, resume_agent, wait_agent, and close_agent (stable; on by default)" (https://learn.chatgpt.com/docs/config-file/config-reference).
  - v2 `spawn_agent` parameters are `task_name` and `message` (required), plus `agent_type`, `fork_turns` (`all|none`), `model`, and `reasoning_effort` (`core/src/tools/handlers/multi_agents_spec.rs`).
  - The v1 version has `fork_context` instead of `fork_turns`.
- **Custom agents.**
  - Docs: "add standalone TOML files under ~/.codex/agents/ for personal agents or .codex/agents/ for project-scoped agents." Required fields are `name`, `description`, `developer_instructions`. Optional fields are `model`, `model_reasoning_effort`, `model_reasoning_summary`, `model_verbosity`, `features.*=false`, and `skills.config`. (SA)
  - Config: `[agents] enabled, max_concurrent_threads_per_session` ("When unset, Codex chooses the default"; legacy alias `max_threads`), `default_subagent_model`, `default_subagent_reasoning_effort`, `interrupt_message`, `agents.<name>.description`, and `agents.<name>.config_file`.
- **Sandbox.** "Subagents inherit the parent turn's current sandbox and approval settings… A custom agent file can't replace those settings." "Custom agent instructions can ask an agent to avoid edits, but they don't create a separate read-only sandbox." (SA)
- **Plugins and skills cannot ship agents.**
  - `agent-roles/src/loader.rs` discovers roles only at `layer.config_folder().join("agents")` (that is, `~/.codex/agents` and `<repo>/.codex/agents`) and `[agents.<role>]` entries.
  - There is no plugin path.
  - The docs tell Claude plugin authors to convert agents to skills (§1).
  - So a plugin can only *instruct* delegation. This is an inference from the source plus the docs.
- **How to run parallel reviewers today.** The documented prompt pattern is: "Spawn one agent per point, wait for all of them, and summarize the result for each point." Another example: "Review this branch with parallel subagents. Spawn one subagent for security risks, one for test gaps, and one for maintainability. Wait for all three…" (SA)
- **Official precedent.**
  - `superpowers/skills/requesting-code-review/` ships `code-reviewer.md` as a prompt template inside the skill folder.
  - `codex-security/skills/finding-discovery/SKILL.md` says: "use file-review subagents when they are available".
- **Built-in review.**
  - `codex exec review [--uncommitted|--base B|--commit SHA]`, from the local `--help`.
  - The bundled system skill `review-agent` has `allow_implicit_invocation: false` and a fixed `[P1] Title — path:line` format (`codex-rs/skills/src/assets/samples/review-agent/`).

## 5. Hooks

- **Format.** `hooks.json` is `{"hooks": {Event: [{"matcher"?, "hooks": [{"type":"command","command","statusMessage"?,"timeout"?,"additionalContextLimit"?}]}]}}`.
  - Events: `PreToolUse, PermissionRequest, PostToolUse, PreCompact, PostCompact, UserPromptSubmit, SubagentStop, Stop, Interrupt, SessionStart, SubagentStart, SessionEnd`.
  - "Non-managed hooks must be reviewed and trusted before they run." Codex "records trust against the hook's current hash." (https://learn.chatgpt.com/docs/hooks)
- **Plugin eligibility.**
  - "Lifecycle hooks are supported for plugins installed manually in Codex desktop. Plugins containing lifecycle hooks aren't eligible for the public plugin directory." (PB)
  - "Plugin ZIP packages containing app references (apps / .app.json) or lifecycle hooks cannot currently be submitted." (https://developers.openai.com/plugins/deploy/submission)
  - "Plugin hooks are not supported in cloud-orchestrated ChatGPT Work." (https://learn.chatgpt.com/docs/plugins)
  - The hooks doc also says Codex "can also discover hooks bundled with enabled plugins" (the CLI is not excluded there). Whether CLI-installed plugin hooks run is ambiguous in the docs (UNVERIFIED).
  - `--dangerously-bypass-hook-trust` exists for automation (`codex exec --help`).

## 6. Evals

- **`codex exec --json` events** (`codex-rs/exec/src/exec_events.rs`):
  - `thread.started{thread_id}`, `turn.started`, `turn.completed{usage{input_tokens, cached_input_tokens, cache_write_input_tokens, output_tokens, reasoning_output_tokens}}`, `turn.failed{error}`, `item.started|updated|completed{item}`, `error{message}`.
  - `item.type` is one of:
    - `agent_message{text}`
    - `reasoning{text}`
    - `command_execution{command, aggregated_output, exit_code, status: in_progress|completed|failed|declined}`
    - `file_change{changes[{path, kind: add|delete|update}], status}`
    - `mcp_tool_call{server, tool, arguments, result, error, status}`
    - `collab_tool_call{tool: spawn_agent|send_input|wait|close_agent, sender_thread_id, receiver_thread_ids, prompt, agents_states, status}`
    - `web_search`
    - `todo_list{items[{text, completed}]}`
    - `error`
- **Non-interactive runs.** "By default, codex exec runs in a read-only sandbox." "--full-auto is no longer supported. Update scripts to use --sandbox workspace-write." Other relevant flags: `--output-schema`, `-o/--output-last-message`, `--ephemeral`, `--ignore-user-config`, `--ignore-rules`, `--skip-git-repo-check`. (https://learn.chatgpt.com/docs/non-interactive-mode)
- **OpenAI eval blog** (https://developers.openai.com/blog/eval-skills, 2026-01-22): "use codex exec --json so your eval harness can score what actually happened" and "write deterministic checks against command_execution events". It also recommends a CSV with `should_trigger` covering explicit, implicit, and negative-control rows, and `--output-schema` rubrics. The blog's `--full-auto` examples are now stale.
- **plugin-eval** (`openai/plugins/plugins/plugin-eval`, `.codex-plugin` format):
  - Commands: `start`, `analyze`, `explain-budget`, `measurement-plan`, `init-benchmark`, `benchmark`, `report`, `compare`. "analyze, explain-budget, and measurement-plan are deterministic local workflows."
  - **Static checks** (`src/evaluators/skill.js`, `plugin.js`):
    - `frontmatter-extra-keys`. Allowed keys: `name, description, license, allowed-tools, metadata, disable-model-invocation, user-invocable, context, agent, …`
    - `description-too-long` (>1024)
    - `description-trigger-weak` (no "use when")
    - `skill-large` (>500 lines) and `skill-too-large` (>800)
    - `progressive-disclosure-missing` (>350 lines and no `references/`)
    - `broken-relative-links`, `extra-doc-files`
    - Manifest checks: name in hyphen-case, name matches the directory, default prompts not too many or too long, `brandColor`, skills present.
  - **`.plugin-eval/benchmark.json`** (`src/core/benchmark.js`):
    - `{kind:"plugin-eval-benchmark", runner{type:"codex-cli", model, sandbox:"workspace-write", approvalPolicy:"never", extraArgs}, workspace{sourcePath, setupMode:"copy", preserve:"on-failure"}, targetProvisioning{mode: "isolated-skill-home"|"workspace-plugin-marketplace"}, verifiers{commands[]}, scenarios[{id,title,purpose,userInput,successChecklist}]}`
    - It runs `codex exec --json --ephemeral --skip-git-repo-check --cd <ws> --output-last-message <f> -s <sandbox> -c approval_policy=… -m <model>`.
  - **Deterministic pass/fail:** yes, through verifiers. Each command runs as `/bin/zsh -lc <cmd>` in the workspace, `status: code===0 ? "passed" : "failed"`, and a scenario is `completed` only if Codex succeeded and all verifiers passed. `successChecklist` is free text and is not auto-graded.
  - The default models are hard-coded `gpt-5.4`/`gpt-5.4-mini`, so pass `-m`.

## 7. Official authoring guidance

- **Descriptions.**
  - "write concise descriptions with clear scope and boundaries. Front-load the key use case and trigger words." (SK)
  - "The description determines when the model considers the skill… Put detailed procedure, format, and safety instructions in the body." (https://developers.openai.com/plugins/build/skills)
  - "Keep discovery cheap and precise… Avoid exhaustive capability lists and catchalls" (`codex-rs/skills/src/assets/samples/skill-creator/SKILL.md`).
- **Scope.** "Keep each skill focused on one job." "Write imperative steps with explicit inputs and outputs." (SK) "Prefer one focused skill… Split workflows when they have different triggers, inputs, or success criteria." The same page has a testing matrix: direct, indirect, incomplete, should-not-activate, and edge cases.
- **Size.**
  - No hard limit in the Codex parser beyond name ≤64.
  - Plugin-eval heuristics: 500/800 lines and a 1024-character description.
  - The skill-creator suggests `short_description` of 25–64 characters.
  - Avoid "a `README.md`… or other auxiliary documentation" in skills (skill-creator).
- **Submission.**
  - Packages must have "skills/<name>/SKILL.md, with valid name and description fields."
  - "Skills are automatically scanned"; "Skills-only plugins may be subject to additional eligibility requirements."
  - No hooks and no `.app.json`.
  - Requires "Apps Management write access" and "identity verification."
  - Replace "Claude-specific references … with provider-neutral language, such as 'the model.'"
  - Sources: https://developers.openai.com/plugins/deploy/submission, https://developers.openai.com/plugins/plugin-guidelines, https://developers.openai.com/plugins/guides/submit-claude-plugin.

## Implications for the review slice (all inference)

1. **Packaging.** Ship a portable root `plugin.json` (Agent Plugins `$schema`) with `skills/code-review/`. Add `extensions.com.openai.interface` only if it is wanted for presentation. Do not ship plugin-root `agents/`, `commands/`, or `hooks/`. Codex ignores or converts them, and hooks block public submission.
2. **Explicit-only invocation.** Set `policy.allow_implicit_invocation: false` in `skills/code-review/agents/openai.yaml`. The SKILL.md key `disable-model-invocation` is ignored by Codex, so the Claude adapter and the Codex adapter need different switches. Users invoke with `$<plugin>:code-review`.
3. **Name.** Avoid the name `review-agent` (a bundled system skill) and any confusion with `codex exec review`. Choose a distinct skill name.
4. **Parallel reviewers.** A plugin cannot define custom agents. Express the five reviewers as SKILL.md instructions instead: spawn one subagent per perspective with `fork_turns: none`, pass the perspective file path and the collected context, then wait for all five. Keep the five perspective knowledge files under `skills/code-review/references/perspectives/`. `.codex/agents/*.toml` is optional and repo-local only.
5. **Concurrency limit.** `agents.max_concurrent_threads_per_session` defaults to an undocumented value (UNVERIFIED). The procedure should tolerate fewer than five concurrent agents by queueing or sequencing them, and still require all five results.
6. **Read-only cannot be enforced per reviewer.** Reviewers inherit the parent sandbox, and an agent file cannot narrow it. The procedure should state "do not edit". Contract tests should run with the default read-only sandbox and assert there are zero `file_change` items.
7. **Context script.** Put the POSIX script in `skills/code-review/scripts/` and reference it by a skill-relative path. In the trace it appears as a `command_execution` item, so a test can assert that it ran and exited 0.
8. **Fixed findings format.** Validate with `--output-schema` (JSON) or `-o last.md` plus a deterministic parser. The bundled `review-agent` `[P1] Title — path:line` convention is a reasonable precedent.
9. **Contract tests.** Use `codex exec --json --ephemeral -s read-only`. Assert `collab_tool_call` items with `tool=="spawn_agent"` count == 5, the context-script `command_execution`, no `file_change` items, and the final-message format. Add negative-control prompts to confirm the skill is not triggered implicitly. The mapping of v2 tool names (`wait_agent`, `followup_task`) onto the `CollabTool` enum is UNVERIFIED, so validate it empirically first.
10. **plugin-eval.** It is useful for static lint and for `verifiers.commands` exit-code gating. It assumes the `.codex-plugin` layout and zsh verifiers, so the neutral core's own test runner should stay authoritative.
